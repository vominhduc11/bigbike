## TL;DR (tóm tắt cho người quản lý)

Giao diện admin **chạy tốt trên màn hình desktop**, nhưng **trên điện thoại/tablet nhiều trang bị lỗi**: các **bảng dữ liệu dài bị cắt mất cột bên phải** (không cuốn ngang được, không xếp lại thành thẻ), một số **biểu mẫu và trang cấu hình bị bóp méo** vì layout cố định. Khung sườn chung (menu trượt + nút ba gạch) thì **đã làm responsive sẵn**. Phần lớn lỗi đến từ **một vài nguyên nhân gốc lặp lại** — sửa đúng vài chỗ dùng chung là khắc phục được hàng loạt trang.

Mức độ: **39 màn hình → 8 tốt / 30 một phần / 1 hỏng (Shipping)**. **57 component dùng chung → 42 tốt / 14 một phần / 1 hỏng (MediaListRow)**.

Đề bài giả định đây là dự án **Next.js + Tailwind thuần**. Thực tế khác ở 3 điểm — cần thống nhất trước khi code Phase 2:

| Giả định trong đề bài | Thực tế trong repo |

| "Chỉ dùng Tailwind utility, không custom CSS" | Responsive hiện tại **gần như 100% nằm trong CSS `@media` viết tay** (35 rule, hệ `bb-*` + layout primitives). Chỉ có 26 Tailwind responsive prefix trong toàn app (10 file). Ép sang Tailwind thuần = viết lại 39 màn — **mâu thuẫn với hướng redesign đã duyệt** (re-skin qua token + CSS, không rewrite). |
| "Xây sidebar collapse + mobile nav drawer" | **Đã có sẵn**: drawer trượt + overlay + nút hamburger, kích hoạt ở `900px` ([AdminShell.jsx](src/components/AdminShell.jsx), [admin-prototype.css:1147](src/styles/admin-prototype.css#L1147)). **Hệ quả:** Phase 2 nên là **sửa/bổ sung `@media` CSS sẵn có + vá vài class dùng chung**, không phải convert sang Tailwind. Các điểm cần user quyết được liệt kê ở Mục 5.

> **Docs-First:** Đây là thay đổi thuần layout/markup/CSS, không đụng API / data contract / permission / state machine, nên **không kích hoạt nghĩa vụ đọc business docs** (theo CLAUDE.md: "không cần đọc docs khi thay đổi thuần style"). **Ngoại lệ cần lưu:** một số lỗi là *class CSS không tồn tại* (xem RC-2/RC-3) — đây là bug layout tiềm ẩn; CLAUDE.md yêu cầu không gộp bug-fix lạ vào task khác, nên cần user xác nhận có vá luôn trong Phase 2 không.

Tailwind defaults: sm 640 / md 768 / lg 1024 / xl 1280 / 2xl 1536 (this repo has no custom 4xl token; 4xl below refers to ultra-wide >=1920).

| Tailwind tier | Status in bigbike-admin |
|---|---|
| **sm** (640) | COVERED at 640px - heavily used as a custom CSS breakpoint (10+ @media max-width:640 blocks across all 3 files) AND matches the 26 inline Tailwind sm: prefixes. This is the most consistent tier. |
| **md** (768) | NOT covered at 768px. The codebase deliberately uses 720, 760, and 900 instead (720: dash-table, cat-thumb-popover, form-media-pair; 760: audit table->card; 900: the primary tablet/drawer tier). Inline md: prefixes exist (~several of the 26) but there is NO 768px custom @media rule, so md handling is fragmented across 720/760/900 rather than a single 768 line. |
| **lg** (1024) | PARTIALLY covered. Custom CSS uses 1024px in 2 places (admin-layout show/hide-on-tablet table->card; admin-prototype bb-grid-2/2-1 stacking). Inline lg: prefixes also appear. But the dominant tablet tier is 900px, not 1024, so 1024 handling is thin. |
| **xl** (1280) | WEAK. Tailwind xl: (1280) prefixes are rare among the 26 inline uses, and there is NO custom @media at 1280px. The breakpoint-policy comment notes 1280 as 'no issues' (content area 972px under the 1400 cap), so it is intentionally under-handled. |
| **2xl** (1536) | WEAK / effectively unhandled. No custom @media at 1536px and 2xl: inline prefixes are essentially absent. The closest desktop-up rule is min-width:1400px (bb-kpi-grid -> 6 cols). Policy comment treats 1536 as 'still under 1400 cap' so no special handling. |
| **4xl** (~1920) | Handled only at 1920px via index.css min-width:1920 (.screen max-width 1700). No Tailwind 4xl token usage; this is a single bespoke ultra-wide container-expansion rule, not a general scale tier. |

### Structural breakpoint gaps (from the CSS map agent)

- No 768px (Tailwind md) breakpoint anywhere in custom CSS. The md tier is split across 720/760/900, so a screen relying on inline md: utilities will not align with any chassis @media rule - behavior between 641-899px is inconsistent (some things switch at 720, some 760, some wait until 900).
- xl (1280) and 2xl (1536) are effectively unhandled in custom CSS: zero @media rules at those widths and near-zero inline xl:/2xl: usage. Layouts between 1201px and 1920px rely entirely on the 1400px .screen max-width cap and a single min-width:1400 KPI rule, so wide-but-not-ultrawide monitors get little tailoring.
- Responsiveness is almost entirely opt-in via specific bb-*/layout/feature class names. Any screen built from bespoke fixed-width markup (custom grids with px columns, fixed-width inline-styled blocks) that does NOT use these classes or inline sm:/md: prefixes will NOT adapt - it only looks fine because desktop is the design baseline.
- The breakpoint-policy comment in admin-layout.css documents a 901-1200px icon-only 64px collapsed sidebar tier, but no such @media rule exists in any of the 4 files - the sidebar only has full (>=901) and full-width drawer (<=900) states. The documented compact-sidebar tier is unimplemented.
- Many data tables rely on a horizontal-scroll wrapper (.table-scroll-wrap, .menu-table-wrap, .bb-table-wrap min-width, .admin-table min-width:760) rather than a true card collapse. Only Audit Log and the show-on-*/MobileCardList screens actually convert tables to cards; other tables just scroll sideways on mobile.
- Fixed-width overlays/panels: .mediadetail-panel (420px) and several modals use min(px,vw) caps but the media detail panel and roles dialogs assume desktop width; only partial mobile-sheet treatment exists (audit filter sheet, au-modal-footer at 480). No global modal->fullscreen-sheet pattern.
- Tailwind responsive prefixes are concentrated in just 10 files (26 total occurrences), 7 of them in two product/content detail screens - the vast majority of screens carry zero inline responsive prefixes and depend solely on shared CSS classes.

## 5. Đề xuất Phase 2 & các quyết định cần user chốt

### 5.1 Thứ tự thực hiện đề xuất (đã điều chỉnh theo thực tế codebase)

Bám đúng thứ tự ưu tiên của đề bài (shell → component dùng chung → page nhiều lỗi nhất), nhưng nội dung là **sửa CSS `@media` + class**, không convert Tailwind:

1. **Layout shell & fix một-nơi-nhiều-trang (làm trước, hiệu quả cao nhất):**
   - **RC-1**: đổi `.bb-table-wrap` → `overflow-x: auto` (1 dòng, gỡ "cắt cụt" cho ~17 màn ngay).
   - **RC-7**: thêm `max-h-[90vh] overflow-y-auto` + lề ngang vào `ui/dialog.jsx` (sửa mọi modal).
   - **RC-4**: vá 2 lưới inline 200px (SettingsScreen, ShippingScreen).
   - **RC-2/RC-3**: sửa các class không tồn tại (`grid-2`→`bb-grid-2`, `row-menu`→`bb-row-menu`, …) — *cần user duyệt vì là bug layout (xem 5.2)*.
   - Shell: thêm tầng "sidebar thu gọn chỉ-icon" 901–1200px nếu chọn theo spec (xem 5.2).
2. **Component dùng chung:** RC-6 (flex-wrap cho BulkActionBar, PaginationControls), RC-8 (cap width popover), RC-9 (MediaListRow), RC-5 (info-grid).
3. **Page theo độ nặng:** ưu tiên bảng 7–9 cột (Coupon, Receivables, Redirect, Return, Warranty, ProductList, OrderList) → áp `MobileCardList` theo khuôn AuditLog; rồi tới Dashboard, Inventory, POS, Menu; cuối cùng các form/detail.

### 5.2 Quyết định cần chốt trước khi code (đề bài yêu cầu dừng & flag)

Đề bài ghi rõ: *"Nếu gặp file có custom breakpoint hoặc logic responsive phức tạp — flag lại, không tự ý quyết định."* Toàn bộ admin là hệ breakpoint tự chế, nên đây là các điểm cần user quyết:

- **Q1 — Cách tiếp cận:** Sửa/bổ sung **CSS `@media` sẵn có** (đúng hướng redesign đã duyệt, ít rủi ro) — *hay* ép **Tailwind utility thuần** như đề bài (= viết lại 39 màn, churn lớn, lệch hướng đã duyệt)?
- **Q2 — Thang breakpoint:** **Chuẩn hoá** toàn bộ về thang Tailwind (sm640/md768/lg1024/xl1280/2xl1536 — đụng mọi `@media`, rủi ro hồi quy) — *hay* **giữ thang bespoke** (640/900/1024) và chỉ vá lỗ hổng (md 768, xl 1280)?
- **Q3 — Sidebar:** Làm đúng spec **3 trạng thái** (ẩn `<md` / chỉ-icon ở `md` / đầy đủ ở `lg+`) — *hay* giữ **2 trạng thái hiện tại** (drawer `<900` / đầy đủ `≥900`) và chỉ tinh chỉnh breakpoint?
- **Q4 — Class bug (RC-2/RC-3):** Có **vá luôn** các class không tồn tại trong Phase 2 không (chúng vừa là bug layout vừa chặn responsive) — hay tách thành task riêng theo nguyên tắc CLAUDE.md?
- **Q5 — Bảng dữ liệu:** Mục tiêu tối thiểu là **cuộn ngang** (nhanh, RC-1) hay đầy đủ **xếp thành thẻ** trên mobile (đúng UX, tốn công hơn, theo khuôn AuditLog)?
